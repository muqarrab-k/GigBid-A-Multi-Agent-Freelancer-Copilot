# RAG notes (hypothesis material)

## Proposal crowd-out in V0 (2026-11-14)

V0 searches every chunk type with the whole job post as the query. On the 95 dev bid jobs,
448 of the 475 top-5 hits were past **proposals** (`evals/results/rag_v0.json`). Proposals are
written in answer to job posts, so they read like the query, and they are about 70% of all
chunks. The gold evidence (`relevant_evidence_ids`) covers only case studies, READMEs, reviews
and code, so V0 scores Recall@5 0.023, MRR 0.046, nDCG@10 0.030.

Restricting the same V0 search to portfolio types (case study, README, review, code, CV)
gives Recall@5 0.235, MRR 0.405, nDCG@10 0.316
(`evals/results/rag_v0_only_case_study_readme_review_code_cv.json`). That run is a diagnostic,
not a variant: V0 stays as the honest baseline.

Hypotheses for later variants:
- H1: Any variant that separates proof (case studies, code, reviews) from phrasing (past
  proposals) beats V0 by a wide margin; the type filter alone is worth about +21 points of
  Recall@5. The agent-facing default now searches portfolio types and asks for proposals
  explicitly.
- H2: Requirement decomposition (V1) helps most on jobs listing four or more requirements,
  because the whole-post query is dominated by boilerplate.
- H3: Outcome-aware ranking (V4) should use proposals for phrasing and style signals, not as
  evidence of experience.
- H4: Code chunks rarely win with whole-post queries; multi-vector items (V5) should lift README
  and code recall for projects whose README is generic.

## Hypothesis for the variant study (stated 2026-11-15, before any variant run)

Portfolio-type filtering + requirement decomposition + hybrid retrieval raises Recall@5 by
15+ points over V0 on dev bid jobs with 4+ requirements, and by less on jobs with fewer.
A cross-encoder rerank adds a few more points on top. The corrective loop (V8) should not
change ranking metrics much, but should refuse on most skip jobs that hit a persona gap.

## Variant study results (2026-11-15)

All numbers are from `evals/results/rag_results_table.md` (regenerated by `scripts/make_rag_table.py`)
and `evals/results/rag_ablation.json`, on the 95 dev bid jobs (70 with 4+ analyst requirements,
25 with fewer). Requirements come from the analyst's cached JobSpec replies, plus new qwen3:4b
calls (with the gpt-oss-20b fallback) for jobs that had none (`evals/results/rag_requirements.json`).
The reranker is BAAI/bge-reranker-v2-m3 on Apple MPS over the top 30. Variant knobs live in
`rag/variants/presets.yaml`. `agent/config.yaml` is a strict schema owned by another work stream,
so only `rag.variant` points there.

| Variant | Recall@5 | MRR | nDCG@10 | R@5 4+ reqs | p50 ms |
|---|---|---|---|---|---|
| V0 dense | 0.0232 | 0.046 | 0.0302 | 0.0257 | 90.1 |
| type filter | 0.2351 | 0.4048 | 0.3162 | 0.24 | 63.9 |
| filter + hybrid (ships) | 0.2554 | 0.4748 | 0.3478 | 0.2486 | 64.8 |
| filter + decomposition | 0.1474 | 0.298 | 0.23 | 0.1486 | 213.9 |
| filter + rerank | 0.1319 | 0.2608 | 0.192 | 0.1257 | 5885.6 |
| filter + decomp + hybrid | 0.1958 | 0.4046 | 0.2975 | 0.1971 | 398.4 |
| filter + decomp + hybrid + rerank | 0.1193 | 0.2688 | 0.1902 | 0.1257 | 2191.2 |

Ablation of the best combination (filter + hybrid). Dropping the filter costs 0.2386 Recall@5;
dropping hybrid costs 0.0203 Recall@5 and 0.07 MRR.

V8 corrective loop (filter, pass score 0.3) refuses 45/110 (0.4091) gap-skip jobs, but also refuses
33/95 (0.3474) bid jobs. Its top-10 ranking is worse (Recall@5 0.1368 vs 0.2351) because the
rewritten keyword query replaces the original one whenever the first pass is weak. A sweep of the
pass score is stored in each V8 result. At 0.1 on top of the reranker stack, it refuses 0.2273 of
gap-skip jobs and 0.0842 of bid jobs: still too blunt to stand in for the fit matcher's gap check.

**What ships and why.** `rag.variant: v2_filter`, i.e. portfolio-type filter + BM25/dense hybrid
with RRF. It has the best Recall@5, MRR and nDCG@10, and is as fast as V0 (p50 64.8 ms). The Portfolio
server picks it up through `get_retriever()`, and an explicit `types` argument (e.g. proposals)
still overrides the filter. Better retrieval did *not* help in two places.

- **Requirement decomposition hurt** (0.2351 → 0.1474 with the filter, even on the 4+ requirement
  jobs: 0.24 → 0.1486). The short requirement queries ("experience with Python") match short,
  skill-dense client reviews best. Reviews make up 232 of the 475 top-5 slots, against 110 of 473
  gold items, so they push out the case studies that carry the gold.
- **The cross-encoder rerank hurt** (0.2351 → 0.1319) and cost about 90x the latency. bge-reranker
  scores raw relevance to the job text, and it favours code chunks: 86 top-5 slots against 3 gold
  code items. Our gold marks project-level proof (case studies, READMEs) as relevant.

Both regressions come from a mismatch between "text that mentions the skill" and "evidence of
having done the project". A stronger text matcher widens that gap; it does not close it.

**Hypothesis: rejected.** On 4+ requirement jobs, filter + decomposition + hybrid does beat V0 by
17.1 points (0.0257 → 0.1971). But all of that gain comes from the type filter: decomposition takes
5.2 points away from filter + hybrid (0.2486 → 0.1971 on the same jobs). The 4+ jobs do not gain
more than the rest (0.2486 vs 0.2747 for filter + hybrid). Rerank subtracts rather than adds.
H1 (proof vs phrasing separation is the main lever) holds; H2 does not.
